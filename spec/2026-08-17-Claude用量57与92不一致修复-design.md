# Claude 用量 57% 与 92% 不一致修复

日期：2026-08-17
状态：已实现并完成本机验证

## 结论

刘海的 57% 不是 Claude 官方额度。官方网络取数持续失败后，界面降级到了本地日志估算；
本机 `~/.claude` 日志实际来自 DeepSeek，所以这个数字从数据源开始就是错的。

Claude Desktop 已经把自己获取的官方 `/usage` 响应写进 Chromium 磁盘缓存。当前本机缓存
于 17:29:39 更新，解压后得到：

- 5 小时：92%
- 7 天：21%

这与 Claude 客户端一致。

## 数据源选择

### 采用：Claude Desktop 本地响应缓存

读取：

```text
~/Library/Application Support/Claude/Cache/Cache_Data/*_0
```

只识别 URL 为 `https://claude.ai/api/organizations/{org}/usage` 的 Chromium Simple Cache
条目，从条目中读取 Claude Desktop 已经收到的 JSON。当前响应使用 zstd 压缩。

优点：

- 不新增网络请求，不会触发 429
- 不读取或解密 token、Cookie、Keychain
- 数值与 Claude Desktop 来自同一份官方响应
- Claude Desktop 更新缓存后，刘海可直接复用

限制：

- 这是 Claude Desktop 的内部缓存格式，未来版本可能变化；解析失败时必须软失败
- 客户端没有刷新用量缓存时，刘海只能显示最后一次官方值，并按时间标记过期
- Chromium 刷新同一接口时可能写入新的缓存文件；读取器每次都按修改时间选择最新条目，不能永久锁定首次命中的旧文件
- 当前机器依赖已有的 Homebrew `zstd`；找不到时回到现有网络兜底

### 不采用：本地 audit 日志作为完整主数据源

`local-agent-mode-sessions/**/audit.jsonl` 确实含服务器返回的 `rate_limit_event`，但低于警戒线
时通常只有重置时间、没有 utilization；当前最新事件只有 90%，不能覆盖完整 0–100% 区间。

### 不采用：Claude Code statusline 作为本机主数据源

Claude Code 2.1.80 起官方支持 `rate_limits.five_hour.used_percentage`，且无需额外 API 请求。
但本机没有配置 statusline，且用户级 Claude Code 当前指向第三方 provider；它不能稳定代表
Claude Desktop 的统一账号额度。代码保留兼容，但不把它作为本次主方案。

## 展示规则

1. 新鲜的 Claude Desktop 官方缓存优先
2. 缓存仍在当前额度周期时继续显示旧值并等待 Desktop 刷新；仅缓存缺失、已跨过重置时间或用户手动刷新时保留网络兜底与失败退避
3. 官方来源都不可用时显示 `—`，不再用本地 token 块估算冒充账号额度
4. 过期官方值可以保留，但沿用现有 UI 降低透明度，不能表现成实时数据

## 安全边界

- 缓存只读，不复制、不修改、不删除
- 不记录缓存原文、组织 ID、请求 ID
- 单个候选文件最大读取 1 MiB
- 只执行固定可信路径的 `zstd`，不通过 shell、不继承任意 PATH 命令
- 不改 `ClaudeAPIService` 和 `CodexUsageProvider`

## 验证结果

1. 缓存解析器从当前 Claude Desktop 缓存读出 92% / 21%
2. `swift build` 和 `swift build -c release` 通过
3. 已新增解析测试，覆盖百分比、重置时间、非官方估算数据和过期窗口；
   当前 Command Line Tools 缺少 Swift `Testing` 模块，所以项目全部测试暂时无法启动
4. 新鲜官方缓存存在时，独立测试版运行中没有建立 Claude TCP 连接
5. 缓存不存在或过期时，保留现有低频网络退避逻辑
6. 所有官方来源不可用时，刘海显示 `—` 而不再显示本地 57% 估算
7. 独立测试 App 已完成签名验证并成功运行；原 `Claude Notch.app` 未覆盖
